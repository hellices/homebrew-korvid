# Homebrew Bottle Distribution Design

## Goal

Make `brew install hellices/korvid/korvid` install Korvid without contacting
`files.pythonhosted.org` on supported macOS systems. Keep the generated source
formula as the reproducible fallback for unsupported systems and explicit
`--build-from-source` installs.

The first supported bottle targets are:

- Apple Silicon on macOS 15 (`arm64_sequoia`)
- Intel on macOS 15 (`sequoia`)

Apple Silicon is the immediate priority because it is the current installation
blocker. Both architectures use the same workflow so neither becomes a
second-class release path.

## Constraints

- A maintainer, never automation, decides whether to merge a pull request.
- `Formula/korvid.rb` remains generated by
  `scripts/generate_homebrew_formula.py` in `hellices/korvid`.
- Homebrew must continue to reach the formula through the tap name rather than
  a file path.
- A partial or failed matrix build must not publish a usable-looking release or
  update the formula.
- Published bottle assets are immutable. A rerun may recover missing
  automation around them but may not silently replace them.

## Chosen Approach

Build bottles in this tap after a source formula update reaches `main`.

This is preferable to building on the formula pull request because it avoids
carrying artifacts across trust boundaries and workflow runs. It is preferable
to moving bottle production into `hellices/korvid` because the tap can test the
exact formula commit and Homebrew layout that users consume without another
cross-repository token or an unmerged formula.

The workflow also supports `workflow_dispatch`, allowing the current Korvid
version to be bottled without waiting for another upstream release.

## Architecture

### Build jobs

For a push, a preflight job reads the formula version and stops successfully
when that version already has a complete `bottle do` block. This prevents the
bottle pull request merge from recursively starting another build.

A matrix runs on `macos-15` and `macos-15-intel`. Each job:

1. Checks out the exact formula commit without persisted credentials.
2. Sets up Homebrew.
3. Symlinks the checkout into Homebrew's tap directory.
4. Runs strict audit.
5. Installs the formula with `--build-bottle`.
6. Runs `brew test` and checks `korvid --version`.
7. Runs `brew bottle --json` with the versioned GitHub Release URL as
   `root_url`.
8. Uploads the bottle archive and JSON metadata as workflow artifacts.

The bottle root URL uses a tap release tag derived from the formula version,
for example:

`https://github.com/hellices/homebrew-korvid/releases/download/korvid-0.2.0`

### Publish and formula-update job

The publish job depends on every matrix leg and therefore cannot run after a
partial build. It:

1. Downloads both bottle archives and their JSON metadata.
2. Validates that the metadata describes one formula version, both expected
   platform tags, the configured root URL, and the downloaded archive hashes.
3. Creates a draft GitHub Release and uploads every validated file.
4. Publishes the release only after all uploads succeed.
5. Uses Homebrew's JSON merge command to write the `bottle do` block into the
   checked-out formula.
6. Commits the formula-only change to a version-specific bottle branch using
   force-with-lease for safe reruns.
7. Opens a pull request, or updates the existing pull request for that branch.
8. Explicitly dispatches the repository test workflow on the bottle branch so
   checks run even though events created with `GITHUB_TOKEN` are normally
   suppressed.

The workflow never merges or enables auto-merge.

A per-version concurrency group allows a rerun to replace an older in-progress
run, while builds for different formula versions remain independent.

### Formula generation lifecycle

The upstream generator continues to emit a source-only formula. A new version
therefore replaces the previous formula and its bottle block in the normal
formula bump pull request. After that pull request is merged, this tap builds
new bottles and opens a second pull request containing the new version's
checksums.

This separation prevents stale bottle metadata from being copied to a new
version and avoids teaching the upstream generator about artifacts that do not
exist until after its output is merged.

## Idempotency and Failure Handling

The versioned bottle release has three states:

- **Absent:** create it as a draft, upload all files, validate them, and publish.
- **Draft:** replace draft assets with the current complete validated set, then
  publish. Draft assets are not user-facing.
- **Published:** do not replace assets. Download the archived JSON and bottles,
  validate their version, platform tags, and checksums, and use them to recover
  a missing branch or pull request.

Commands use strict shell error handling. Invalid version extraction, missing
matrix output, unexpected bottle tags, checksum mismatches, release conflicts,
and push lease failures are fatal and visible in the workflow logs.

## Verification

### Bottle build verification

Each architecture must pass:

- `brew audit --strict`
- source installation with `--build-bottle`
- `brew test`
- installed command version check
- bottle metadata and archive checksum validation

### Bottle consumption verification

The bottle-update pull request runs a macOS test on each matching architecture.
On a fresh runner it removes source caches, blocks both IPv4 and IPv6
resolution of `files.pythonhosted.org`, and runs the normal tap command:

`brew install --verbose hellices/korvid/korvid`

The test requires Homebrew's output to report that it poured the expected
bottle and then checks `brew test` and `korvid --version`. A resource download
attempt cannot fall back to the source path because the blocked host makes the
install fail.

### Source fallback verification

The existing Linux and macOS tests keep the explicit
`brew install --build-from-source` path. Weekly execution continues to detect
yanked or unavailable source distributions even when no repository file
changes.

## Air-Gapped Installation Documentation

The README will distinguish restricted and fully air-gapped operation:

- A normal restricted-network install needs access to the bottle release host
  and Homebrew dependency bottle hosts, but not PyPI.
- An operator can download Korvid's matching bottle in advance and fetch the
  required Homebrew dependency bottles into a transfer directory.
- Those files can be mirrored internally or copied to the target machine.
- A fully disconnected installation must pre-stage both Korvid and all
  Homebrew dependency bottles; the Korvid bottle alone is insufficient.

The documented commands will derive the matching bottle from Homebrew metadata
rather than asking users to guess an architecture-specific filename.

## Out of Scope

- Linux bottles
- Supporting macOS releases other than macOS 15 in the first iteration
- Bundling Homebrew-managed dependencies inside the Korvid bottle
- Automatically merging formula or bottle pull requests
- Changing Korvid's Python extras or source dependency graph
